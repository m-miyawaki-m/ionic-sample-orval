# API Viewer 比較・スコアリング — Redoc / Swagger UI / Stoplight Elements

`openapi/openapi.yaml` を元に静的 HTML を生成する 3 種類のツールを並走させて比較。

このプロジェクトは **3 つ全部を同時に生成可能**：

```powershell
.\scripts\build-api-docs.cmd            # docs/api-reference.html         (Redoc)
.\scripts\build-api-docs-swagger.cmd    # docs/api-reference-swagger.html (Swagger UI)
.\scripts\build-api-docs-elements.cmd   # docs/api-reference-elements.html (Stoplight Elements)
```

ブラウザで全部開いて見比べてみてほしい。

## 4. 各ツールの詳細評価

### 🥇 Redoc（41 / 50） — このプロジェクトの推奨デフォルト

**強み**

- **CLI 1 発で生成**：`@redocly/cli build-docs` 一行で 1 ファイル HTML
- **2 カラム固定レイアウト**：左にエンドポイント・スキーマ、右にコード例。視線移動が最小
- **印刷で崩れない**：「API 仕様書を A4 で配布する」ユースケースに圧倒的に強い
- **動作が軽い**：4 KiB の HTML + 約 2 MB の Redoc バンドルで完結
- **自己完結 HTML**：`@redocly/cli build-docs` は CDN リンクすら使わない単体 HTML を吐く

**弱み**

- **Try it out が無料版に無い**（Redocly Pro / Reference API のみ）
- カスタマイズ範囲は `theme: { ... }` 程度に限定
- レイアウトは選べない（常に 2 カラム）

**こんな時に最適**

- 学習プロジェクトのデフォルト（**今ここ**）
- 仕様書を PDF / 印刷で配布したい
- 公開用の綺麗なドキュメントサイトを作りたい

### 🥈 Swagger UI（37 / 50） — API を試したい時の決定版

**強み**

- **「Try it out」が無料で使える**：ボタン 1 つで実 API を叩いてレスポンス確認
- **業界標準**：誰でも見たことがあるレイアウトで馴染みやすい
- **Spring Boot の Springdoc が標準採用**：BE 起動時の `/swagger-ui.html` と同じ見た目で統一できる
- **OAuth / API Key 認証の入力 UI が組み込み済み**

**弱み**

- **デザインが古い**（2014 年から構造はほぼ同じ）
- **検索機能が貧弱**：Ctrl+F で目視探索しがち
- **印刷で崩れる**：accordion が広がったり閉じたりで PDF 化に向かない
- **タイトル数が増えると遅い**：100 endpoints 超えると重い

**こんな時に最適**

- 開発者がドキュメントから直接 API を叩いて手元で動作確認したい
- BE の Springdoc UI と統一したルック&フィールにしたい
- OAuth / API Key などの認証フロー込みで動作確認したい

### 🥈 Stoplight Elements（37 / 50） — 見た目とナビゲーションが最強

**強み**

- **モダンな 3 カラム UI**：左サイドバー / 中央詳細 / 右コード例
- **超強力な検索**：エンドポイント名・スキーマ名・タグを横断
- **Web Component なので埋め込みが楽**：`<elements-api>` 1 行で他の HTML に貼れる
- **タグでカテゴリ表示が綺麗**：API が増えた時に効く

**弱み**

- **CDN ロード前提**：ネット接続が無いと動かない（オフライン化は手間）
- **「Try it out」も Pro 機能**（無料版でモック呼出はできるが OAuth 等は不可）
- **ドキュメントが Stoplight プラットフォーム前提**で書かれていて取っ付きにくい
- **印刷・PDF が苦手**：3 カラムのまま縮小されて読みにくい

**こんな時に最適**

- API が 30 endpoints を超えて目視で探すのが辛い
- 公開用ポータルで「綺麗な API カタログ」を見せたい
- React / Vue アプリ内に埋め込んでドキュメントタブを作りたい

## 5. ユースケース別の推奨（決定木）

```
[1] API を叩いて手元で動作確認したい？
    └─ YES → Swagger UI 一択
    └─ NO  ↓

[2] 印刷・PDF で配布する予定がある？
    └─ YES → Redoc
    └─ NO  ↓

[3] エンドポイントが 30 個以上ある？ or 公開ポータルで見せたい？
    └─ YES → Stoplight Elements
    └─ NO  → Redoc (デフォルト推奨)
```

## 6. 並走運用のメリット

このプロジェクトでは **3 つを同時に持つ**選択をした：

```
docs/
├─ api-reference.html            ← Redoc（デフォルト）
├─ api-reference-swagger.html    ← Swagger UI（API 動作確認用）
└─ api-reference-elements.html   ← Stoplight Elements（モダン UI 検証）
```

メリット：

- **同じ yaml を 3 つの見た目で同時に検証**できる → どのツールが自分達に合うか判断しやすい
- **将来 1 つに絞り込む時の判断材料**になる
- **新メンバーへの教材**として「同じ仕様書でも UI で印象が変わる」を体感できる

デメリット：

- 仕様変更時に **3 つとも再生成**する必要がある
  - ただしどれも HTML 5 KiB 程度（CDN ロード）で軽量、再生成コストは低い

> 全部一括で生成する派なら：
> ```powershell
> node scripts\_build-html.js all
> .\scripts\build-api-docs.cmd
> ```

## 7. 結論：このプロジェクトのデフォルト

| 場面 | 推奨ツール | 理由 |
|------|---------|------|
| **新メンバーが最初に見る仕様書** | **Redoc** | 1 ファイル・印刷可・読みやすい |
| **API を直接叩いて動作確認** | Swagger UI | Try it out が動く |
| **公開ポータル候補の検証** | Stoplight Elements | 一番モダン |

**`docs/api-reference.html`（Redoc）をプロジェクト標準のドキュメント**としつつ、必要に応じて他 2 つも参照する運用がおすすめ。

## 8. スコアリングの限界

このスコア表は **2026 年 5 月時点**の評価で、以下の前提で付けた：

- このプロジェクトの規模（4 endpoints）
- 学習・プロト用途
- 日本語混じりの仕様
- Windows 環境

**条件が変わると評価も変わる**：

- 100 endpoints 超 → Elements の検索が支配的に有利
- 認証 API がある → Swagger UI の Try it out が圧倒的に便利
- 公開ポータル化 → Redoc / Elements が同点で競る
- B2B SaaS のドキュメント → 商用 Redocly Reference Pro が候補に上がる（要有料判断）

スコアは **「この時点・この前提での選択判断材料」** として読んでほしい。半年後に別の評価をしても良い。
