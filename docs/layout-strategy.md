# Vue + Ionic レイアウト管理戦略（Android アプリ）

本ドキュメントは「Ionic Vue でモバイルアプリを組む際の標準レイアウト・コンポーネント構成」を整理した設計リファレンスです。
対象：本リポジトリ (`frontend/`) を含む、Capacitor + Ionic Vue で Android を主ターゲットとするアプリ。

関連: [vuetify-vs-ionic-vue.md](./vuetify-vs-ionic-vue.md)

---

## 1. 想定する標準フロー

```
[Menu] ──▶ [Search + List] ──▶ [Detail]
              │  ▲                 │  ▲
              ▼  │                 ▼  │
           [Dialog]              [Dialog]
```

業務アプリで最頻出のフロー。本ドキュメントはこの 3 画面 + ダイアログ 2 種を「基準形」として全パターンを設計する。

---

## 2. コンポーネント階層（5層構成）

```
pages/        ルーティング先。IonPage 必須。1ファイル1ルート。
  ├─ MenuView.vue
  ├─ ListView.vue
  └─ DetailView.vue

layouts/      共通枠（IonPage + Header + Content）。slot で差分吸収。
  └─ AppLayout.vue

organisms/    業務ロジックを持つ複合 UI。複数の atoms/molecules + API 呼び出し。
  ├─ ItemSearchBar.vue
  ├─ ItemList.vue
  ├─ ItemFormDialog.vue
  └─ ConfirmDialog.vue

molecules/    小さい組み合わせ。ロジックは持たない。
  ├─ IconTextButton.vue
  ├─ LabeledValue.vue
  └─ MenuCard.vue

atoms/        最小単位。Ionic コンポーネントの薄いラッパ。
  ├─ BaseButton.vue
  └─ BaseInput.vue
```

**依存方向**は上から下のみ（pages → layouts → organisms → molecules → atoms）。逆参照禁止。

## 3. ナビゲーションパターン 5案

レイアウトの「骨格」になるナビゲーション構成の選択肢。各案で「ホーム / 一覧 / 詳細」の 3 画面フローをワイヤーフレームで示す。

### 3.1 Pattern A: シンプル Stack 型（現状）

```
   起動                       タップ                タップ
┌─────────────┐           ┌─────────────┐       ┌─────────────┐
│  ◀ 商品一覧│           │  ◀ 詳細   ✏│       │ Modal出現   │
├─────────────┤           ├─────────────┤       ├─────────────┤
│ りんご  ¥150│  ──tap──▶│ 商品名:    │ ─tap─▶│ 編集フォーム│
│ みかん  ¥120│           │  りんご     │       │             │
│ ぶどう  ¥480│           │ 価格:      │       │ [保存]      │
│             │           │  ¥150      │       │             │
│        ＋  │           │             │       │             │
└─────────────┘           └─────────────┘       └─────────────┘
```

- **構成**: `IonRouterOutlet` 1本のみ
- **向き**: 機能 1〜2 個。本リポジトリの現状
- **長所**: 最小コスト、迷子にならない
- **短所**: 機能が増えると navigation が破綻

- **構成**: Home が `MenuCard` のグリッド、各カードから Stack push

- **構成**: `IonTabs` + 各タブ内に独立した `IonRouterOutlet`（戻る履歴がタブ毎に独立）

- **構成**: `IonSplitPane` + `IonMenu`（phone は drawer、tablet 以上で常時展開）
- **向き**: 機能 5+ 個、設定や管理メニューが多い業務系
- **長所**: 機能をいくらでも追加可能、tablet 対応がタダで付いてくる
- **短所**: メニューが「隠れる」ので発見性が低い、初見ユーザーに不親切

### 3.5 Pattern E: タブ + Drawer ハイブリッド

```
   起動                          ☰タップで補助メニュー
┌─────────────┐              ┌──────┬──────┐
│ ☰ ホーム  🔔│             │ Menu │ホーム│
├─────────────┤              ├──────┼──────┤
│ 今日の売上  │              │📊 レポ│売上 │
│  ¥45,200   │  ──tap──▶  │👥 顧客│     │
│             │              │📑 履歴│     │
│ 新着 3件    │              │⚙ 設定│     │
│             │              │ヘルプ│     │
├─────────────┤              ├──────┼──────┤
│🏠 🔍 📦 ＋  │              │      │🏠 🔍 │
└─────────────┘              └──────┴──────┘
   ▲ 主要4機能      ▲ Drawer に「あまり使わない機能」を退避
```

- **構成**: `IonTabs`（主機能）+ `IonMenu`（補助機能）。FAB（＋）を中央タブに
- **向き**: 機能 6+ 個で、主要機能と補助機能の濃淡がはっきりしている業務アプリ
- **長所**: 「よく使う」と「たまに使う」を物理的に分けられる
- **短所**: 実装複雑度が一段上がる。ユーザーに「どこに何があるか」の学習コスト

### 3.6 比較サマリ

| 観点 | A: Stack | B: メニューホーム | C: ボトムタブ | D: Drawer | E: ハイブリッド |
|------|:-:|:-:|:-:|:-:|:-:|
| 想定機能数 | 1〜2 | 3〜6 | 3〜5 | 5+ | 6+ |
| 主要機能への到達 | 直接 | 1タップ | 0タップ | 1タップ | 0〜1タップ |
| 機能追加コスト | × | ◎ | △(タブ数上限) | ◎ | ◎ |
| Android らしさ | △ | △ | ◎ | ○ | ◎ |
| 初見ユーザーの分かりやすさ | ◎ | ◎ | ○ | △ | △ |
| 実装コスト | 最小 | 小 | 中 | 中 | 大 |
| tablet 対応の楽さ | × | △ | △ | ◎ | ◎ |

### 3.7 本プロジェクトへの推奨

「Menu → 検索+一覧（ダイアログ）→ 詳細（ダイアログ）」というフロー像と Android ターゲットを踏まえ：

- 機能数が読めない / 業務的な「メニュー画面が欲しい」感覚があるなら → **Pattern B**
- 主要機能が 3〜4 個に絞れていて Android らしい UX を狙うなら → **Pattern C**

タブレット展開や大規模化の可能性が見えてきたら **D → E** への移行も視野に。

## 4. ダイアログパターン

### 4.1 ダイアログの種類（8 種）

Ionic Vue が標準提供するオーバーレイ系コンポーネント。すべて Android ハードウェアバックに対応している。

| 種類 | 用途 | trigger | dismiss |
|------|-----|---------|---------|
| `IonAlert` | 確認・短い入力（1〜2フィールド） | declarative / imperative | ボタンタップ・hw-back |
| `IonActionSheet` | 選択肢（2〜5個） | declarative / imperative | swipe down・backdrop・hw-back |
| `IonModal` (bottom sheet) | 中規模フォーム・補助情報 | declarative / imperative | swipe down・backdrop・hw-back |
| `IonModal` (full screen) | 大規模フォーム・ウィザード | declarative / imperative | close ボタン・hw-back |
| `IonPopover` | コンテキストメニュー・吹き出し | trigger element 指定 | tap outside・hw-back |
| `IonToast` | 非ブロッキング通知（成功/失敗） | imperative | 自動 dismiss・swipe |
| `IonLoading` | ブロッキング処理中インジケータ | imperative | 処理完了で自動 dismiss |
| `IonPicker` | wheel 選択（日時・連動セレクト） | declarative | confirm / cancel |

### 4.2 用途別フローチャート

```
ユーザーに通知だけ？
├─ Yes ──▶ IonToast
│         （アクション付き例:「削除しました [元に戻す]」）
└─ No  ──▶ ユーザー入力が必要？
    ├─ Yes ──▶ 入力量は？
    │         ├─ Yes/No ─────────────────▶ IonAlert
    │         ├─ 1 フィールド ────────────▶ IonAlert (inputs)
    │         ├─ 数フィールド ────────────▶ IonModal (bottom sheet)
    │         └─ 大量 / 複数ステップ ─────▶ IonModal (full screen)
    └─ No  ──▶ 選択肢の数は？
              ├─ 2〜4 ───────────────────▶ IonActionSheet
              ├─ メニュー的（要素に紐付き）─▶ IonPopover
              └─ wheel 系（日時等）──────▶ IonPicker
   ─────────────────────────────────────────────────
   ▶ 非同期処理を待たせたい ───────────────▶ IonLoading（他操作禁止）
```

### 4.4 実装方式: Declarative vs Imperative

ダイアログは 2 種類の開き方がある。

| 観点 | Declarative<br>`<IonModal :is-open="show">` | Imperative<br>`modalController.create()` |
|------|---|---|
| コードの見やすさ | ◎（template に状態と一緒に書ける） | ○（呼び出し箇所が分散しがち） |
| 動的に複数開く | ✕ | ◎ |
| 返り値の受け取り | `@willDismiss` イベント + emit | `await modal.onDidDismiss()` |
| Pinia / Composable から開く | △（state を template まで届ける必要） | ◎（どこからでも呼べる） |
| テストしやすさ | ◎ | ○ |

**プロジェクト規約**:
- 単純な開閉・1 画面に紐付くダイアログ → **Declarative**
- グローバルな確認・どの画面からも呼ぶもの（`useConfirm()` 等の composable） → **Imperative**

### 4.5 共通ダイアログ部品候補

業務アプリで何度も書くダイアログは organism として切り出す。

| 部品 | 中身 | 想定 API |
|------|-----|----------|
| `ConfirmDialog` (composable) | IonAlert ベース、Promise を返す | `await confirm('削除しますか？')` |
| `ItemFormDialog` | IonModal (bottom sheet)、新規/編集兼用 | `<ItemFormDialog v-model="open" :item="..." @save="..."/>` |
| `useToast` (composable) | IonToast の薄いラッパ | `toast.success('保存しました')` |
| `useLoading` (composable) | present/dismiss を try/finally で隠蔽 | `await withLoading(async () => api.save(...))` |
| `ActionMenuPopover` | IonPopover ベース、メニュー項目を props で受ける | `<ActionMenuPopover :items="..." :trigger="..."/>` |

### 4.6 ダイアログ階層ルール

- **Alert > Toast**: Alert（ブロッキング）の上に Toast（通知）は重ねない（被って読めなくなる）
- **Modal の中で Modal**: Ionic は技術的には可能だが、UX が破綻するので **1 階層まで**
- **Loading の dismiss 忘れ**: `await ionLoading.present()` した後は **finally で必ず `dismiss()`**（バグの温床）。`useLoading` で隠蔽推奨
- **Toast の position**: Android は `position="bottom"` が自然。ただし FAB がある画面では `position="top"` を検討（FAB と被る）
- **Picker は full screen Modal の中で開くな**: z-index が破綻する。フォーム入力中の日時選択は inline の `IonDatetime` を使う

### 4.7 絶対に守る制約

1. **自前 `v-if` で作るダイアログは禁止**。Android ハードウェアバックで閉じない＝UX 破綻
2. **必ず `IonModal` / `IonAlert` / `IonActionSheet` か `modalController.create()` 経由**
3. **bottom sheet は `breakpoints` と `initialBreakpoint` 必須**。指定なしだと iOS/Android で挙動差
4. **`IonLoading` は present/dismiss を try/finally でペアに**。グローバル loading state より局所が安全
5. **削除確認は `IonAlert` の destructive スタイル**（赤ボタン）を使う。タップミス防止

## 6. ボタンコンポーネント（IconTextButton）

業務アプリで頻出の「アイコン + ラベル」ボタンを 1 コンポーネントで吸収。

```
┌──────────────────────────────────────────────────────┐
│ variant="icon-only"                                  │
│   ┌─────┐                                            │
│   │  ＋ │     ← サイズ 40×40。一覧のヘッダー等        │
│   └─────┘                                            │
├──────────────────────────────────────────────────────┤
│ variant="icon-text"                                  │
│   ┌──────────────┐                                   │
│   │  ＋  追加    │   ← 主アクション。詳細画面の保存   │
│   └──────────────┘                                   │
├──────────────────────────────────────────────────────┤
│ variant="text-only"                                  │
│   ┌──────────────┐                                   │
│   │   キャンセル │   ← ダイアログのサブアクション      │
│   └──────────────┘                                   │
├──────────────────────────────────────────────────────┤
│ variant="icon-text" color="danger" fill="outline"    │
│   ┌──────────────┐                                   │
│   │  🗑  削除    │   ← 破壊的操作                     │
│   └──────────────┘                                   │
└──────────────────────────────────────────────────────┘
```

**Props 設計（仕様メモ）**

| prop | 型 | 既定 |
|------|----|----|
| `variant` | `'icon-only' \| 'icon-text' \| 'text-only'` | `'icon-text'` |
| `icon` | `string`（ionicons の named import） | – |
| `label` | `string` | – |
| `color` | `'primary' \| 'danger' \| 'medium'` | `'primary'` |
| `fill` | `'solid' \| 'outline' \| 'clear'` | `'solid'` |
| `size` | `'small' \| 'default' \| 'large'` | `'default'` |
| `disabled` | `boolean` | `false` |

`variant="icon-only"` で `label` 必須は a11y 担保のため（`aria-label` に流し込む）。

## 8. 現プロジェクトからの移行ステップ

`frontend/src/` の現状（`ListView.vue` / `DetailView.vue` / `CreateView.vue` / `BridgeDemoView.vue`）をベースに、最小コストで導入する順序：

| Step | 作業 | 効果 |
|------|------|------|
| 1 | `layouts/AppLayout.vue` 新設 | ヘッダー重複除去 |
| 2 | `molecules/IconTextButton.vue` 新設 | ボタン UI 統一 |
| 3 | 既存 4 View を AppLayout でリファクタ | コード量 ~30% 削減見込 |
| 4 | `CreateView.vue` → `organisms/ItemFormDialog.vue` 化（IonModal） | バックキー対応・遷移コスト削減 |
| 5 | （任意）Side Menu or Tabs 導入 | 画面数増加時 |

Step 1〜4 は既存機能の挙動を変えないリファクタとして実施可能。

## 9. 守るべき制約

1. **`IonPage` は各 View のルート要素**。AppLayout 側に置くのは OK だが、AppLayout を更にラップしない。
2. **ダイアログは Ionic 標準 API 経由**（`IonModal` / `IonAlert` / `IonActionSheet`）。自前 `v-if` は禁止。
3. **依存方向**は pages → layouts → organisms → molecules → atoms の単方向。
4. **`IconTextButton` の `variant="icon-only"` は `label` 必須**（a11y）。
5. **bottom sheet を使う場合は `breakpoints` と `initialBreakpoint` 必須**。指定なしだと挙動が iOS/Android で差が出る。

## 10. 実装サンプル（本リポジトリ）

本ドキュメントで定義した 5 パターンを実際に動くサンプルとして本リポジトリに実装済み。

| エントリ | パス | レイアウト | 主な動作 |
|---------|------|-----------|----------|
| サンプル一覧 | `/` | `SamplesIndexView.vue` | 5 パターン + 既存デモへの入口 |
| Pattern A | `/samples/a` | Simple Stack | 一覧 → 詳細 |
| Pattern B | `/samples/b` | Menu Home | ダッシュボード → 一覧 → 詳細 |
| Pattern C | `/samples/c` | Bottom Tabs | ホーム / 商品 / 設定 タブ |
| Pattern D | `/samples/d` | Side Drawer | IonSplitPane + IonMenu |
| Pattern E | `/samples/e` | Tabs + Drawer | 主機能タブ + 補助 drawer |

### データ取得スタック

各サンプルは `useItems()` / `useItem(id)` composable 経由で API データを取得する。

```
OpenAPI (openapi/openapi.yaml)
  ↓ orval gen
src/api/default/default.ts          ← axios client (listItems, getItem, ...)
src/api/zod/default/default.zod.ts  ← zod schema (ListItemsResponse, ...)
  ↓
src/composables/useItems.ts         ← axios 呼び出し + zod.parse() でランタイム検証
  ↓
各 *ListView.vue / *DetailView.vue
```

### MSW

dev 環境は `.env.development` の `VITE_USE_MOCK=msw` により MSW が自動起動し、
OpenAPI examples をベースとした生成 handler が `/api/items` 系を返す。
本番 API（Spring Boot）が起動していなくても全パターンが動作する。

## 11. 他に検討できる要素

実装サンプルは「レイアウト構造のデモ」を目的とした最小実装。プロダクション化する際の検討事項：

### データ層
- **状態管理**: 現状は composable 内 `ref` のみ。複数画面で同じデータを共有する場合は **Pinia** で `useItemsStore()` 化を検討
- **データキャッシュ**: stale-while-revalidate が欲しければ **Tanstack Query (vue-query)** 導入
- **API キャンセル**: `axios.ts` は cancelToken を生成しているが composable が活用していない。unmount 時の自動キャンセル未実装
- **オフライン対応**: Capacitor + Service Worker / IndexedDB / Capacitor Preferences でのキャッシュ層未対応
- **zod の nullable / optional**: OpenAPI で `nullable: true` を使う場合の orval-zod 出力は要検証

### UI 層
- **共通 AppLayout 未抽出**: §2 で推奨した `AppLayout.vue` をサンプルでは各 View に重複展開している（学習用に明示的に書いた）。プロダクションでは抽出推奨
- **Skeleton Loading**: 現状 "Loading..." テキスト。`IonSkeletonText` で体感改善余地
- **Pull-to-Refresh**: `IonRefresher` を各一覧に追加可能だが未実装
- **無限スクロール**: `IonInfiniteScroll` + ページング API 対応が必要（現 API はページング未対応）
- **ダイアログ部品**: §4.5 で示した `ConfirmDialog` / `useToast` / `useLoading` / `ItemFormDialog` 等は未実装
- **Detail View の編集**: 5 パターンとも詳細画面は read-only。プロダクトでは編集 Modal 起動が必要
- **a11y**: アイコンのみボタンの `aria-label`、Picker のフォーカス管理は未整理

### ナビゲーション層
- **Pattern E の Drawer 位置**: 右側 (`side="end"`) で実装。Material Design 規約では左側が主流。プロダクトでは要相談
- **ハードウェアバック処理**: Capacitor `App.backButton` イベントで「dialog 閉じ > menu 閉じ > 戻る」の優先順位を明示する設計が要る
- **Deep Link**: Capacitor `App.appUrlOpen` 経由で外部 URL から特定パターンを開く対応未実装

### 横断
- **i18n**: 日本語ハードコード。`vue-i18n` 導入で多言語化可能
- **ダークモード**: `dark.system.css` 読み込み済みだが、各 View の配色未検証
- **テスト**: 新規 5 パターンの View にはユニットテスト/ E2E 未追加（既存 4 View は P0–P3 で網羅済み）
- **コード分割**: 現状 vendor bundle が 1MB 超え。`build.rollupOptions.output.manualChunks` で改善余地
