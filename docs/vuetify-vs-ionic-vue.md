# Vuetify と Ionic Vue の併用検討

## 概要

Vuetify と Ionic Vue は **役割が重複する競合関係** にあり、併用は技術的には可能ですが、現在のモバイル PoC（Ionic + Vue + Capacitor）の文脈では **おすすめしません**。両者とも UI コンポーネントライブラリで、ボタン・カード・入力欄など同じ部品を別々の思想で提供しているため、デザインの一貫性・バンドルサイズ・ルーティングの 3 点で衝突が起きやすいです。

もし Vuetify の特定機能（データテーブルなど）が欲しい場合は、全体を Vuetify にするのではなく、Ionic を土台にして必要箇所だけ別の Vue 向けライブラリ（ag-grid-vue、vue-chartjs など）を足す方が安全です。

---

## 両者の位置づけ

**Vuetify** は Material Design に準拠した Web 向け UI フレームワークで、PC ブラウザを主戦場に設計されています。グリッドシステム、タイポグラフィ、テーマ機構を独自に持ち、`v-btn` `v-card` `v-data-table` といった豊富なコンポーネントを提供します。

**Ionic Vue** はモバイル特化の UI フレームワークで、Web Components（Stencil 製）として実装されています。iOS では iOS 風、Android では Material 風に **プラットフォーム適応** する点が最大の特徴で、`ion-router-outlet` による独自ルーティング、`ionViewWillEnter` などのライフサイクル、スワイプバック・モーダル管理など、ネイティブアプリの UX 再現に最適化されています。

つまり「同じ Vue 3 向けの UI ライブラリ」という点では同じレイヤーで、共存というより **選択する** ものです。

---

## 併用したときに起きる具体的な問題

### 1. デザインシステムの二重化

Vuetify の Material Design と Ionic のプラットフォーム適応スタイルが同じ画面に混在し、見た目の統一感が崩れます。iOS 実機で見たときに、Vuetify のボタンだけ無理やり Android 風に出てくる、という現象が起きます。

### 2. CSS 特異性の衝突

両者ともグローバル CSS を大量に注入します。`color` `padding` `background` あたりが上書きし合い、`!important` の応酬になりがちです。CSS 変数の命名空間も `--v-*`（Vuetify）と `--ion-*`（Ionic）で別物です。

### 3. ルーティングとライフサイクルの非互換

Ionic は `IonRouterOutlet` を使うことで、ページキャッシュ・遷移アニメーション・戻る挙動を制御しています。Vuetify のコンポーネント内で通常の vue-router ナビゲーションを混ぜると、Ionic の遷移管理から外れたページが生まれ、戻るボタンや状態保持が壊れます。

### 4. オーバーレイ管理の競合

モーダル、トースト、ダイアログを両者がそれぞれ管理しています。`v-dialog` と `ion-modal` を同時に開くと z-index 競合が起きやすく、Capacitor のキーボード制御・セーフエリア対応も Ionic 側に最適化されているため、Vuetify のモーダルでは挙動が崩れます。

### 5. バンドルサイズ

両者ともそれなりに重い（Vuetify 本体 ~400KB、Ionic Vue + コンポーネント ~500KB 級）ため、両方入れるとモバイル初回起動が体感で重くなります。Tree-shaking しても重複領域があります。

## 本 PoC での推奨判断

現状の構成（Ionic + Vue + Capacitor、業務端末向け AAR ブリッジ）はモバイル業務アプリ寄りなので、**Ionic Vue 単体でいく** のが筋がいいと考えます。理由は 3 つです。

- **(a)** Capacitor のプラグイン群（StatusBar、Keyboard、SafeArea 等）は Ionic と噛み合うように作られていること
- **(b)** 端末配布想定なら起動時間・APK サイズに有利
- **(c)** 後で iOS 対応も視野に入るならプラットフォーム適応の恩恵が大きいこと

足りない部品があるときの対処としては、まず Ionic の公式コンポーネントで代替できないか確認し、それでもダメな場合に限ってフレームワーク非依存の Vue 3 ライブラリを **部分的に** 入れる、という方針が安全です。

| 用途       | 候補ライブラリ                          |
| ---------- | --------------------------------------- |
| チャート   | `vue-chartjs`、`apexcharts/vue3`        |
| データグリッド | `ag-grid-vue3`、`@tanstack/vue-table` |

これらは UI フレームワークではなく単機能ライブラリなので、Ionic と競合しません。

---

## Vuetify が活きる場面

Vuetify を採用するとしたら、別途 **社内向け管理画面（PC Web アプリ）** を作る話が出てきたときが好機です。そちらは Ionic と真逆の要件（複雑なテーブル、フォーム、ダッシュボード）なので Vuetify が強みを発揮します。

> 「モバイル ＝ Ionic ／ PC 管理画面 ＝ Vuetify」と用途で分けるのが、いちばん整理しやすい構成です。

---

## まとめ

| 観点                 | 結論                                                            |
| -------------------- | --------------------------------------------------------------- |
| モバイル PoC 単体    | **Ionic Vue 単体**を推奨                                        |
| Vuetify 併用         | 非推奨（デザイン・ルーティング・バンドルサイズで衝突）          |
| 不足機能の補い方     | フレームワーク非依存の単機能ライブラリを部分採用                |
| Vuetify を使う場面   | PC 管理画面など別アプリで独立採用                               |

検討中の具体的なユースケース（どの Vuetify コンポーネントが欲しいか、など）が定まれば、それに合わせた代替案をもう少し絞り込めます。
